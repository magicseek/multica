# Agent Workflow Template Strategy

## Goal

Move agent execution workflows out of hardcoded Go templates and into editable, workspace-level workflow definitions. Workflows should behave like first-class configuration alongside Runtimes and Skills, while preserving deterministic execution through queue-time snapshots.

## Decisions

### Workflow ownership

Workflow definitions are workspace-level resources. Projects bind to a default workflow so all issues in the same project follow the same work process even when reassigned to another agent.

Issue-level overrides are allowed for small bugs, research tasks, or one-off work. Overrides choose another workflow definition, such as Direct Task or Research Note. They do not bypass workflow governance.

Agent-level default workflow selection is removed from the primary model. Agents may declare capabilities or constraints, but workflow selection remains owned by issue, project, and workspace resolution.

### Resolution order

For issue assignment tasks:

```text
issue workflow override
> project workflow binding
> workspace default assignment workflow
> built-in fallback workflow
```

For comment-triggered `@agent` tasks:

```text
explicit full-workflow request
> workspace default comment workflow
> Comment Response system workflow
```

Comment mentions do not silently inherit a project's full workflow.

### Workflow definitions and revisions

Each workflow definition has versioned revisions:

```text
draft -> published -> deprecated
```

Bindings and overrides point to workflow definition IDs. Queue-time resolution uses the definition's current published revision for the target trigger.

Editing a published workflow creates or updates a draft revision. Publishing a draft makes it the current published revision for new tasks only. Existing queued, running, or historical tasks keep their workflow snapshot.

### Canonical schema

Workflow schema is the only persisted source of truth. Source editor, step graph editor, and preview all read/write the same schema.

Minimum schema shape:

```json
{
  "schema_version": 1,
  "applicability": ["assignment"],
  "source": {
    "format": "markdown",
    "body_template": "..."
  },
  "variables": [],
  "steps": [],
  "gates": []
}
```

Markdown is an editable field and rendered output, not an independent second model.

### System-seeded workflows

Built-in workflows become read-only system-seeded workflow definitions in each workspace:

- Standard Assignment
- Trellis Task
- Direct Task
- Research Note
- Comment Response

Users customize built-ins by copying/forking them into editable workflow definitions. Seeding must be idempotent by workspace and system key.

### Queue-time snapshots

Issue assignment tasks resolve workflow selection when `agent_task_queue` is created, not when a daemon later claims the task.

Each task stores:

- workflow definition ID
- workflow revision ID
- revision number
- trigger type
- original schema
- rendered Markdown
- capability warnings
- resolved timestamp

The daemon consumes the rendered Markdown from the snapshot and does not re-resolve workflow definitions.

### Capability mismatch

First version capability mismatch is warning-only. UI should surface warnings, queue-time snapshot metadata should record them, and execution should continue.

Hard blocking can be added later after real mismatch patterns are known.

### UI direction

Add a Workflows page at workspace scope beside Runtimes and Skills. Use Multica's existing UI library and design system.

Expected surfaces:

- Workflow list with search/filter/status/origin
- Create workflow
- Fork system workflow
- Workflow detail/editor
- Source tab
- Steps tab
- Preview tab with graph preview and rendered Markdown
- Publish flow
- Project binding selector
- Issue override selector
- Capability warning display

Preview must render from workflow schema. It must show a visual graph derived
from `steps[].depends_on` and the rendered Markdown generated by the server
preview contract. Do not copy ai-desk styling; only reuse concepts such as
editable workflow resources, source/schema import/export, graph preview, and
rendered preview.

Preview UX details:

- Rendered Markdown must use the shared app Markdown renderer, not a raw
  monospace source block.
- Graph preview must include a header control to expand it to fill the Preview
  workspace and collapse back to the split graph/Markdown layout.
- The graph canvas must respond to pane size changes by recalculating scale and
  centering the graph, so expand/collapse transitions do not leave the workflow
  anchored to the top-left corner.
- Graph and rendered Markdown panes must scroll independently. Long rendered
  Markdown should never push, resize, or hide the graph preview.
- Source, Steps, and Preview tabs should use consistent icon treatment.
- Steps should read as a numbered ordered editing list with minimal chrome,
  instead of isolated card boxes for every step.

## Proposed Data Model

Core tables:

- `workflow_definition`
- `workflow_revision`

Binding fields:

- `workspace.default_assignment_workflow_definition_id`
- `workspace.default_comment_workflow_definition_id`
- `project.workflow_definition_id`
- `issue.workflow_override_definition_id`

Snapshot fields:

- `agent_task_queue.workflow_definition_id`
- `agent_task_queue.workflow_revision_id`
- `agent_task_queue.workflow_snapshot`

Legacy fields:

- `agent.execution_protocol_enabled`
- `agent.execution_protocol_slug`

Legacy fields should remain temporarily for compatibility and migration, but new resolution should not depend on them as the primary selector.

## Proposed API Surface

```text
GET    /api/workflows?applicability=assignment&include_archived=false
POST   /api/workflows
GET    /api/workflows/{id}
PATCH  /api/workflows/{id}
POST   /api/workflows/{id}/draft
PUT    /api/workflows/{id}/draft
POST   /api/workflows/{id}/publish
POST   /api/workflows/{id}/fork
POST   /api/workflows/preview
```

Existing project and issue APIs should accept workflow binding fields:

```json
{
  "workflow_definition_id": "uuid-or-null"
}
```

```json
{
  "workflow_override_definition_id": "uuid-or-null"
}
```

Daemon claim payload should include workflow snapshot metadata and rendered Markdown.

## Trellis Task Breakdown

### Task 1: Database and seed foundation

Implement workflow definition/revision tables, workspace/project/issue/task fields, sqlc queries, and idempotent system seed logic.

Acceptance:

- migrations apply cleanly
- system workflows seed per workspace
- existing workspaces receive seeds
- system seeds are read-only
- sqlc regenerated

### Task 2: Workflow service and API

Implement workflow CRUD, draft, publish, fork, list filtering, schema validation, and preview endpoint.

Acceptance:

- published lifecycle works
- direct system-seed mutation returns 403
- fork creates editable copy
- invalid schema returns field-level errors
- list filters by applicability/status/origin

### Task 3: Workflow resolver and queue-time snapshot

Implement assignment workflow resolution and snapshot creation when `agent_task_queue` rows are created.

Acceptance:

- precedence order is enforced
- invalid/archived selections fall back safely and record warnings
- publish after queue does not affect queued snapshot
- snapshot includes rendered Markdown and schema

### Task 4: Daemon execution injection

Thread workflow snapshots through daemon claim payloads and inject rendered Markdown into the execution environment.

Acceptance:

- daemon uses snapshot content
- daemon does not resolve workflow definitions
- legacy null snapshot path still works
- existing execenv tests updated

### Task 5: Frontend core contracts

Add TypeScript types, API client functions, React Query keys/options, and path builders for workflows.

Acceptance:

- no direct localStorage/process.env usage in `packages/core`
- query invalidation follows existing Runtimes/Skills patterns
- typecheck passes

### Task 6: Workflows list and editor UI

Build workspace-level Workflows page with list, create, fork, detail/editor, Source/Steps/Preview tabs, graph preview, and publish flow using Multica UI/design system.

Acceptance:

- route appears beside Runtimes and Skills
- editor reads/writes one schema object
- preview shows graph nodes/edges from `schema.steps` and `steps[].depends_on`
- preview uses schema renderer for Markdown
- graph preview expands/collapses inside the Preview tab
- graph content scales and remains centered after expand/collapse
- graph and rendered Markdown panes have independent scrolling
- Source, Steps, and Preview tabs have consistent icons
- Steps editor rows are numbered and avoid heavy per-step card framing
- system seeds show as read-only with fork action
- UI works in web and desktop routes

### Task 7: Project and issue binding UI

Add project workflow binding and issue workflow override selectors with applicability filtering and warning display.

Acceptance:

- project selector shows assignment-compatible published definitions
- issue override selector supports Direct Task and Research Note
- capability mismatch warning does not block assignment
- selection survives reassignment to another agent

### Task 8: Compatibility and cleanup

Preserve old agent execution protocol behavior during rollout, add migration notes, and de-emphasize agent-level protocol selection in UI.

Acceptance:

- existing agents keep working
- no new workflow selection depends primarily on agent slug
- tests cover legacy fallback
- docs explain migration path

## Open Implementation Notes

- Prefer a single shared renderer for server preview and queue-time rendered Markdown.
- Treat ai-desk as a behavior checklist, not just inspiration. When a referenced
  ai-desk workflow editor capability is in scope, write the equivalent Multica
  acceptance item explicitly. For this feature that includes graph preview,
  rendered Markdown preview, schema import/export concepts, and step dependency
  editing.
- Keep schema validation centralized in backend service.
- Do not fork ai-desk UI code; use ai-desk as product reference only.
- Avoid introducing a separate workflow runner in the first implementation. The first implementation injects rendered workflow instructions; richer step execution can build on the stored schema later.
