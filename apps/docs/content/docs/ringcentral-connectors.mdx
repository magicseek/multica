RingCentral connectors are a private deployment feature. They are hidden in default Multica deployments and only appear when the API server starts with the `ringcentral` connector profile.

The profile registers three optional providers:

| Provider | Project resources | Capabilities |
|---|---|---|
| RingCentral GitLab | `ringcentral_gitlab_repo` | Validate token, list branches/MRs, create semantic task branches, commit file actions through the GitLab API, create merge requests |
| RingCentral Jira | `ringcentral_jira_project`, `ringcentral_jira_issue` | Validate token, list projects, search/read issues |
| RingCentral Wiki | `ringcentral_wiki_space`, `ringcentral_wiki_page` | Validate token, search/read spaces and pages |

<Callout type="warning">
Connector credentials are always user-owned. Multica stores encrypted server-side ciphertext, never returns raw tokens, and never injects RingCentral PATs into an agent environment, task prompt, local git config, or `.multica/project/resources.json`.
</Callout>

## Enable the profile

Set the connector profile and credential encryption key on the API server:

```dotenv
MULTICA_CONNECTOR_PROFILES=ringcentral
CONNECTOR_CREDENTIAL_ENCRYPTION_KEY=<32-byte base64/hex/raw key>
```

Restart the API after setting these values. If `CONNECTOR_CREDENTIAL_ENCRYPTION_KEY` is missing or not 32 bytes, startup fails closed before credential storage is exposed.

By default the profile uses the official RingCentral services:

```dotenv
RINGCENTRAL_GITLAB_API_BASE_URL=https://git.ringcentral.com/api/v4
RINGCENTRAL_GITLAB_WEB_BASE_URL=https://git.ringcentral.com
RINGCENTRAL_JIRA_BASE_URL=https://jira.ringcentral.com
RINGCENTRAL_WIKI_BASE_URL=https://wiki.ringcentral.com
```

Operators may still set those environment variables for deployment-level overrides, and workspace owners/admins may override service addresses from Settings -> Integrations.

When `ringcentral` is not present in `MULTICA_CONNECTOR_PROFILES`, the provider registry is empty for RingCentral, Settings does not show the RingCentral section, RingCentral project resource types are rejected, and agent runtime guidance does not mention RingCentral connector commands.

## Configure Settings

Open **Settings -> Integrations**.

Workspace owners and admins can:

- Enable or disable each RingCentral provider for the workspace.
- Edit service addresses when the workspace should use a non-default endpoint.
- Set RingCentral GitLab's remote write policy. GitLab writes require `merge_request_preparation`; read-only commands continue to work when writes are disabled.

Each member configures only their own credentials:

- Paste a provider token into the provider card.
- Multica validates it against the upstream service before saving.
- If validation succeeds, the card shows the upstream identity and validation time.
- If validation fails, the token is rejected and not stored.

## Attach project resources

RingCentral connector commands are scoped by project resources. Attach resources from the project resource surface, not from Settings.

Available resource payloads:

```json
{
  "resource_type": "ringcentral_gitlab_repo",
  "resource_ref": {
    "project_id": "group/repo",
    "default_branch": "main"
  }
}
```

```json
{
  "resource_type": "ringcentral_jira_project",
  "resource_ref": {
    "project_key": "ABC"
  }
}
```

```json
{
  "resource_type": "ringcentral_wiki_space",
  "resource_ref": {
    "space_key": "ENG"
  }
}
```

Pinned Jira issue and Wiki page resources use `issue_key` and `page_id` respectively.

## Agent commands

Agents use `multica connector ...` from inside a daemon-managed task. These commands call the Multica API; the server authorizes the task and invokes the upstream provider with the delegated user's encrypted credential.

The CLI requires daemon-provided `MULTICA_WORKSPACE_ID`, `MULTICA_AGENT_ID`, and `MULTICA_TASK_ID`. Human terminal calls outside a running task are rejected.

GitLab:

```bash
multica connector gitlab branches <project-resource-id> --search release
multica connector gitlab merge-requests <project-resource-id> --state opened
multica connector gitlab create-branch <project-resource-id> --branch feat/ABC-123-work --ref main
multica connector gitlab commit <project-resource-id> \
  --branch feat/ABC-123-work \
  --message "Update workflow docs" \
  --actions-json '[{"action":"update","file_path":"README.md","content":"..."}]'
multica connector gitlab create-mr <project-resource-id> \
  --source-branch feat/ABC-123-work \
  --target-branch main \
  --title "Update workflow docs"
```

Jira:

```bash
multica connector jira search <project-resource-id> --jql 'status = "In Progress"'
multica connector jira issue <project-resource-id> ABC-123
```

Wiki:

```bash
multica connector wiki search <project-resource-id> --cql 'title ~ "runbook"'
multica connector wiki page <project-resource-id> 123456
```

GitLab writes are restricted to attached repositories, non-default/non-protected branches, and semantic task branch prefixes: `feat/`, `fix/`, `refactor/`, `docs/`, `test/`, `chore/`, or `perf/`.

Jira and Wiki are read-only in the MVP. Comments, status changes, page edits, and other external writes are intentionally not exposed.

## Authorization model

Every connector command must pass all checks:

- The provider is registered by the RingCentral profile and enabled for the workspace.
- The daemon request carries `X-Agent-ID` and `X-Task-ID`.
- The task belongs to that agent and is active.
- The task has a connector delegated user captured when it was queued.
- The requested project resource belongs to the task's project and matches the provider.
- The delegated user has a valid credential for the provider.
- The requested capability is enabled and allowed by workspace policy.

Upstream authentication failures mark the delegated user's credential invalid, so the next task sees a recoverable reconfiguration problem instead of silently retrying a bad token.
